# Ubuntu C++ 로컬 ASR 파이프라인 설계 검토 (심층)

작성일: 2026-06-02

대상: "메인 백엔드 프로세스 ↔ 음성인식(전처리 포함) 프로세스 분리, 로컬 모델 구동"
제안서에 대한 아키텍처 심층 검토. **구현 코드는 포함하지 않음.** 설계 결정과 대안,
근거, 측정 기준만 정리한다.

---

## 0. 검토 결론 요약 (TL;DR)

- 프로세스 분리 + UDS + 전처리/추론 스레드 분리라는 **큰 골격은 타당**하다.
- 그러나 실제 목적이 "대리운전 통화에서 금액 인상 **동의(네/오케이) 감지**"라면,
  **full STT(whisper 전사) 중심 설계는 목적 과잉(over-engineering)**이며 지연·정확도·
  안정성 모두에서 불리하다. → **VAD + 키워드 스포팅(KWS) 1차, whisper는 보조/오프라인**.
- 통화 오디오가 **8kHz narrowband(G.711/PCMU)**라는 점이 모든 결정의 전제이며,
  제안서의 "16kHz" 가정은 재검토가 필요하다.
- whisper.cpp는 **진정한 스트리밍 엔진이 아니다**(슬라이딩 윈도우 재디코딩).
  저지연 실시간 키워드 감지 용도로는 부적합하다.
- IPC 코드 힌트에는 **partial read / 결과 프레이밍 누락**이라는 실제 동작 버그가 있다.

---

## 1. 목적 재정의: 이건 "전사"가 아니라 "동의 감지" 문제다

제안서는 STT(전체 문장 전사)를 전제로 설계됐지만, 실제 시나리오는:

> 통화 중 상담원이 금액 인상을 제안 → 고객이 "네 / 그래요 / 올려주세요 / 오케이"라고
> 동의하는지 **여부(boolean + confidence)**를 저지연으로 감지

이는 전형적인 **의도/키워드 감지(Keyword Spotting, Intent Detection)** 문제다.
전체 문장을 텍스트로 받아 후처리로 "네"를 찾는 것은:

| 항목 | full STT 후 키워드 매칭 | 직접 KWS/의도 감지 |
|---|---|---|
| 지연 | 발화 종료 후 디코딩(수백 ms~초) | 발화 중 실시간(수십~수백 ms) |
| CPU | 높음(전체 디코딩) | 낮음 |
| 취객 발음 강건성 | whisper 환각·반복에 취약 | 음향 모델 + 임계값으로 제어 가능 |
| 오탐 제어 | 어려움(텍스트 사후) | confidence threshold로 직접 제어 |
| 구현 복잡도 | 높음 | 중간 |

**결정 권고**: 1차 판단은 KWS, whisper.cpp는 (a) 통화 로그용 전사, (b) 모호 케이스
재확인용 보조로만 사용하는 **하이브리드**.

## 2. 오디오 파이프라인: 8kHz 전제를 먼저 못박아야 한다

### 2.1 소스 포맷
- VoIP/전화망은 거의 항상 **G.711 μ-law(PCMU) 또는 a-law, 8kHz mono**다.
- PCMU 디코딩 → 16-bit PCM, **8kHz, mono**가 자연스러운 1차 산출물.

### 2.2 16kHz 업샘플링의 의미
- whisper 모델 입력은 16kHz이므로 업샘플링이 **필요**하지만,
  업샘플링은 **없는 고주파 대역을 만들어내지 못한다**(정보량 불변).
- 즉 "통화 8kHz → 16kHz → whisper"는 narrowband 음성을 그대로 먹이는 것이고,
  whisper의 한국어 `base/small` 정확도는 이 조건에서 **눈에 띄게 하락**한다.
- 업샘플링은 단순 zero-stuffing이 아니라 **저역통과 보간(polyphase resampler)**으로
  해야 aliasing이 없다. (SpeexDSP의 `speex_resampler` 사용 가능)

### 2.3 채널/프레임 정정
- 제안서 코드의 `buffer(960)` + 주석 "320 samples × 3채널"은 혼동.
- 통화는 **mono**. 16kHz·20ms = **320 샘플**. 8kHz·20ms = **160 샘플**.
- WebRTC VAD와 SpeexDSP는 mono·고정 프레임을 전제하므로 프레임 크기를
  엔진 요구치에 **정확히** 맞춰야 한다(WebRTC VAD: 10/20/30ms만 허용).

## 3. 전처리(SpeexDSP) — 양날의 검

| 처리 | 권장 | 비고 |
|---|---|---|
| Resample 8k→16k | ✅ 필수(whisper 경로) | polyphase, anti-alias |
| AGC | ⚠️ 측정 후 결정 | 취객 음량 편차엔 도움, 과하면 잡음 증폭 |
| Noise Suppression | ⚠️ 측정 후 결정 | **whisper엔 오히려 독이 될 수 있음** |
| Dereverb | △ | 차량 내부 반향엔 도움 가능 |
| VAD | ✅ 필수 | 발화 구간 게이팅 |

핵심 주의: whisper류 모델은 비교적 raw한 오디오로 학습되어, 공격적 NS/AGC가
**인식률을 떨어뜨리는 사례**가 흔하다. 반드시 **on/off A·B를 동일 셋으로 측정**한 뒤
채택할 것. "켜면 좋다"는 가정 금지.

### VAD 선택지
- **WebRTC VAD**: 가볍고 빠르지만 aggressive, 취객의 흐리고 끊기는 발화를 **조기 컷**할 수
  있음.
- **Silero VAD**(ONNX/CPU): 더 강건, 약간 무겁지만 통화 환경에서 오탐/누락이 적음.
- 권장: 초기엔 WebRTC VAD로 시작하되, 동의 누락(취객)이 문제되면 Silero로 교체 가능하도록
  **VAD를 인터페이스 뒤로 추상화**.

## 4. 인식 엔진 비교 — whisper.cpp 단독은 재고

### 4.1 whisper.cpp의 "스트리밍" 실체
- 공식 `stream` 예제는 **고정 윈도우(예: 30초)를 슬라이딩하며 반복 재디코딩**한다.
- 결과적으로 (a) 같은 구간을 여러 번 디코딩해 CPU 낭비, (b) 윈도우를 짧게 잡으면
  정확도 급락, 길게 잡으면 지연 증가 → **저지연·실시간·정확을 동시에 못 잡음**.
- 부분 결과(partial)가 계속 흔들려 "확정 시점" 판단 로직이 별도로 필요.

### 4.2 initial_prompt 바이어싱의 한계
- `"네, 그래요, 올려주세요, 오케이"` 주입은 효과가 **약하고 불안정**하다.
- 무음/짧은 발화에서 whisper는 **prompt 단어를 환각(hallucination)·반복 출력**하는
  것으로 잘 알려져 있다. 즉 "네"를 말하지 않았는데 "네"가 나올 위험 → **동의 오탐**은
  과금/분쟁과 직결되므로 치명적.

### 4.3 엔진 후보 정리
| 엔진 | 강점 | 약점 | 이 시나리오 적합도 |
|---|---|---|---|
| whisper.cpp (base/small) | 셋업 쉬움, 범용 전사 | 비스트리밍, 8kHz 약함, 환각 | 보조/로그용 |
| 키워드 스포팅(KWS) | 초저지연, confidence 제어 | 키워드 한정 | **1차 판단 최적** |
| Vosk (Kaldi 기반, C++) | 진짜 스트리밍, grammar 제약 디코딩, 8kHz 한국어 모델 존재 | 정확도는 whisper보다 낮을 수 있음 | 스트리밍 STT 필요 시 강력 후보 |
| sherpa-onnx (k2/Zipformer) | 스트리밍 RNNT, CPU 빠름, KWS 모드 내장 | 한국어 모델 가용성 확인 필요 | KWS·스트리밍 모두 커버 |

권장 탐색 순서: **sherpa-onnx KWS 또는 Vosk grammar 제약 디코딩**을 1차 PoC로 검토.
"네/그래요/오케이/올려주세요"만 인식하도록 **문법(grammar)을 제약**하면 오탐이 급감하고
지연이 극단적으로 낮아진다. whisper.cpp는 통화 전체 전사 아카이브 용도로 병행.

## 5. IPC / UDS — 골격은 OK, 디테일에 실동작 버그

UDS 선택 자체는 적절(루프백 TCP 대비 오버헤드↓). 다만:

### 5.1 partial read 문제 (실제 버그)
- 스트림형 소켓의 `read()`는 **요청 바이트를 한 번에 다 채워주지 않는다.** 제안서 예제처럼
  `read(fd, buf, frame_bytes)` 한 번으로 한 프레임을 가정하면 **오디오가 어긋난다**.
- 해결: `recv` 루프로 **정확히 N바이트를 채우는 read-fully** 또는 길이 프레이밍 사용.

### 5.2 결과(텍스트) 채널 프레이밍 누락
- 오디오는 연속 바이트 스트림, 결과는 **메시지**다. 같은 스트림에서 메시지를 구분하려면
  **길이 prefix(예: 4바이트 LE length + payload)** 또는 구분자/시퀀스 프레이밍이 필수.
- 권장: 오디오 IN과 결과 OUT을 **소켓/방향을 분리**하거나, 단일 소켓이면 명확한 프레이밍
  프로토콜을 정의.

### 5.3 백프레셔(backpressure)
- 추론이 느려지면 수신 버퍼가 쌓인다. 무한 큐는 메모리 폭증·지연 누적을 부른다.
- 권장: **고정 크기 링버퍼 + 드롭/최신 우선 정책**. 실시간성에선 오래된 오디오를 버리는
  편이 낫다. 큐 깊이/드롭율을 **메트릭으로 노출**.

### 5.4 프레이밍 프로토콜 제안(요지)
```
[오디오 IN]  연속 PCM16LE, 고정 20ms 프레임 (헤더 없음, 스트림)
[결과 OUT]   u32 len(LE) | u8 type(partial/final/state) | u64 ts_ms | payload(UTF-8 JSON)
```

## 6. 지연 시간 예산(Latency Budget)

"실시간성이 생명"이라면 단계별 예산을 명시하고 측정해야 한다(예시 목표):

| 단계 | 목표 |
|---|---|
| PCMU 디코드 + 리샘플 | < 2 ms / frame |
| VAD 판정 | < 1 ms / frame |
| 전처리(AGC/NS) | < 3 ms / frame |
| 추론(KWS) | < 50 ms (발화 중 부분 판정) |
| 추론(whisper small, 보조) | 수백 ms ~ 초 (오프 경로) |
| UDS 왕복 | < 1 ms |
| **동의 감지 end-to-end 목표** | **< 300 ms** |

whisper를 1차 경로에 두면 이 예산을 맞추기 어렵다 → 4장의 KWS 권고와 직결.

## 7. 스레딩 / 버퍼 구조 (권장)

```
[수신 스레드]  UDS read-fully → 고정 링버퍼(lock-free SPSC 권장)
       │ (20ms 프레임)
[전처리 스레드] resample → VAD → (AGC/NS 옵션) → 발화 세그먼트 조립
       │ 발화 active 구간만 다운스트림
       ├──> [KWS 스레드]   부분/확정 동의 판정 → 결과 OUT (저지연 경로)
       └──> [STT 스레드]   세그먼트 종료 시 whisper 전사 → 결과 OUT (로그/보조)
```
- 스레드 간 단일 생산자-단일 소비자 큐로 락 경합 최소화.
- whisper 스레드는 별도라 1차 동의 판정 지연에 영향을 주지 않음.

## 8. 정확도/오탐 평가 전략 (필수)

동의 감지 오탐은 **요금 분쟁**으로 직결되므로 측정 체계가 설계의 일부여야 한다.

- 데이터셋: 실제 통화 유사(8kHz, 차량 소음, 취객 발화) 라벨링 셋 확보.
- 지표: **동의 감지의 Precision/Recall, 특히 FP(오탐)율**, 그리고 감지 지연(ms).
- 운영 정책: confidence 임계값 + (선택) **2-strike 확인**(애매하면 재확인 멘트) 등
  비즈니스 안전장치를 ASR 위에 둔다.
- 회귀 방지: 전처리 on/off, VAD 종류, 모델 크기 조합을 **동일 셋으로 벤치**하고 표로 관리.

## 9. 장애/복구·운영

- AI 프로세스 죽으면 메인은 통화를 떨어뜨리면 안 됨 → **소켓 재연결 + 헬스체크 + 워치독**.
- AI 다운/지연 시 **graceful degradation**: 동의 자동감지 비활성, 상담원 수동 확인으로 폴백.
- 소켓 경로 `/tmp/asr.sock` 권한/스테일 소켓 정리, `SO_REUSEADDR`/언링크 처리.
- 관측성: 큐 깊이, 드롭율, 프레임당 처리시간, 감지 지연, FP/FN 카운터 로깅.

## 10. 단계적 도입 권고

1. **PoC-A**: PCMU→8kHz PCM 디코드 + VAD만으로 발화 세그먼트 추출 검증(엔진 없이).
2. **PoC-B**: sherpa-onnx KWS 또는 Vosk grammar 제약으로 "네/오케이" 감지 PoC,
   FP/FN·지연 측정.
3. **PoC-C**: whisper.cpp를 보조 전사 경로로 병행, 모호 케이스 보강 효과 측정.
4. 전처리(AGC/NS) **A·B 측정 후** 채택 여부 확정.
5. UDS 프레이밍/백프레셔/워치독 등 운영 견고화.

## 11. 제안서 대비 변경 요약

| 제안서 | 본 검토 권고 |
|---|---|
| full whisper.cpp 전사 중심 | KWS/grammar 1차 + whisper 보조 하이브리드 |

| whisper "스트리밍 모드" | 비스트리밍 사실 반영, 스트리밍 필요 시 Vosk/sherpa-onnx |
| initial_prompt 바이어싱 신뢰 | 환각·오탐 위험으로 1차 판단 의존 금지 |
| `read()` 단일 호출 프레임 | read-fully + 길이 프레이밍 + 백프레셔 |
| AGC/NS 기본 적용 | A·B 측정 후 선택 적용 |
| UDS 단일 양방향 | 프레이밍 프로토콜 정의(또는 방향 분리) |

> 파이프라인은 별개 스택의 설계 검토 문서다. 구현 진행 여부는 별도 결정.
